UZ Core Consent содержит собственное решение пациента о том, могут ли его медицинские данные передаваться на Цифровой платформе здравоохранения. В Узбекистане применяется модель отказа (opt-out): если ресурс Consent для пациента отсутствует, обмен данными разрешён по умолчанию; пациент отказывается от обмена, регистрируя Consent, который его запрещает. Модель намеренно является бинарной: одно условие `provision` либо разрешает, либо запрещает доступ, и пациент самостоятельно задаёт решение в портале пациента. Платформа применяет это решение: если Consent запрещает доступ, запрос данных отклоняется с HTTP 403. Предусмотрены два исключения: законный доступ для лечащих специалистов и других уполномоченных законом сторон, а также экстренный доступ break-glass (регистрируемый в [AuditEvent](StructureDefinition-uz-core-auditevent.html) с экстренной целью использования данных). Consent связан с [Patient](StructureDefinition-uz-core-patient.html).

### Обязательные элементы и элементы Must Support

Приведённые ниже элементы должны либо всегда присутствовать (обязательные элементы), либо поддерживаться при наличии данных ([Must Support](must-support.html)). Не все из них обязательны, однако система должна заполнять каждый элемент Must Support, если соответствующие данные имеются, и обрабатывать его при получении. Это человекочитаемое описание; [формальные представления](#profile) ниже содержат точные кардинальности, типы и терминологические привязки.

#### Каждый UZ Core Consent Must Have

Этот профиль не добавляет собственных обязательных кардинальностей. Единственный обязательный элемент унаследован от базового ресурса: `status` - состояние самой записи Consent, связанное с набором значений состояний согласия DHP.

#### Каждый UZ Core Consent Must Support

 

- `subject` - пациент, к данным которого применяется Consent;
- `grantor` - сторона, предоставляющая решение (пациент);
- `period` - начало и окончание периода, в течение которого применяется Consent;
- regulatory basis - нормативное основание, определяющее закон или политику, на которых основано решение (обязательная привязка);
- `decision` - permit или deny (обязательная привязка);
- `source` - либо `sourceAttachment` с url и датой создания, либо `sourceReference`, содержащий исходный документ согласия;
- `provision`, уточняющий решение, с указанием action и purpose (оба элемента имеют обязательные привязки).

> Решение намеренно является бинарным: одно значение `decision` - `permit` или `deny`. Платформа использует его, чтобы разрешить или отклонить каждый запрос данных.

### Пошаговое формирование JSON

Consent в основном формируется системой, когда пациент задаёт решение в портале, поэтому вручную требуется создавать немного данных. Ниже приведена полная запись: скопируйте её и адаптируйте; каждое показанное значение соответствует этому профилю. Полный экземпляр - [пример Consent](Consent-example-consent.html).

#### Минимальный Consent, который следует отправлять

`status` - единственный строго обязательный элемент, однако Consent имеет смысл только тогда, когда указано, чьи данные он охватывает (`subject`), какое решение принято (`decision` - скалярный код `permit` или `deny`) и к чему применяется это решение (`provision`). Поскольку отсутствие Consent уже разрешает обмен данными, обычно отправляемая запись представляет собой отказ (opt-out): `deny`, где `provision.action` указывает, какое действие запрещается - в данном случае раскрытие данных. Каждый ресурс UZ Core также должен указывать профиль, которому он заявляет соответствие, в `meta.profile`:

```json
{
  "resourceType": "Consent",
  "meta": { "profile": ["https://dhp.uz/fhir/core/StructureDefinition/uz-core-consent"] },
  "status": "active",
  "subject": { "reference": "Patient/example-patient" },
  "decision": "deny",
  "provision": [
    {
      "action": [
        { "coding": [{ "system": "http://terminology.hl7.org/CodeSystem/consentaction", "code": "disclose" }] }
      ]
    }
  ]
}
```

`status` и `decision` используют обязательную привязку: значение должно входить в связанный набор значений, перечисленный ниже в представлении Snapshot. `provision.action` имеет тип `CodeableConcept`, поэтому его код размещается в массиве `coding`; `subject` имеет тип `Reference`, поэтому целевой ресурс указывается непосредственно в `reference`.

#### Реалистичная запись Consent

Более полная запись - здесь показано предоставление доступа, например когда пациент повторно разрешает обмен или ограничивает Consent конкретной целью и периодом - также содержит сведения о стороне, предоставившей решение (`grantor`, пациент), периоде действия (`period`), законе, на котором оно основано (`regulatoryBasis`), и `provision`, уточняющем решение для конкретных action и purpose. `grantor` представляет собой список `Reference`, а `regulatoryBasis`, `provision.action` и `provision.purpose` являются кодированными элементами; каждое значение выбирается из связанного набора значений:

```json
{
  "resourceType": "Consent",
  "meta": { "profile": ["https://dhp.uz/fhir/core/StructureDefinition/uz-core-consent"] },
  "status": "active",
  "subject": { "reference": "Patient/example-patient" },
  "grantor": [
    { "reference": "Patient/example-patient" }
  ],
  "period": {
    "start": "2025-02-15T14:02:52+05:00",
    "end": "2026-02-15T14:02:52+05:00"
  },
  "regulatoryBasis": [
    {
      "coding": [
        { "system": "https://terminology.dhp.uz/fhir/core/CodeSystem/consent-policy-cs", "code": "uz-LRU-547" }
      ]
    }
  ],
  "decision": "permit",
  "provision": [
    {
      "action": [
        { "coding": [{ "system": "http://terminology.hl7.org/CodeSystem/consentaction", "code": "disclose" }] }
      ],
      "purpose": [
        { "system": "http://terminology.hl7.org/CodeSystem/v3-ActReason", "code": "RECORDMGT" }
      ],
      "period": {
        "start": "2025-02-15T14:02:52+05:00",
        "end": "2026-02-15T14:02:52+05:00"
      }
    }
  ]
}
```

Обратите внимание: `provision.purpose` имеет непосредственно тип `Coding` и не помещается в массив `coding`, тогда как `regulatoryBasis` и `provision.action` имеют тип `CodeableConcept` и содержат массив `coding`. Эта запись предоставляет доступ; отказ opt-out имеет такую же структуру, но в `decision` указывается `deny`, после чего платформа отклоняет каждый запрос данных с HTTP 403. Правила выбора кодированных значений приведены в разделах [Отсутствующие и скрытые данные](general-guidance.html#missing-data) и [Терминология](general-guidance.html#terminology).
